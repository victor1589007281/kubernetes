## 概述

### 背景

在 Kubernetes 集群中，MySQL 等数据库服务通常需要预留大量内存（如 buffer pool），但实际使用率往往远低于预留值。基于 Linux 内核的**缺页中断（Page Fault）** 机制，内存只在真正访问时才会实际分配物理页面，这为内存超售提供了理论基础。

### 目标

1. **预测 MySQL 内存使用**：基于历史数据预测未来 3 天的内存使用量
2. **实现内存超售**：在不与 k8s 原有内存管理冲突的前提下，通过 cgroup 实现内存超售
3. **监控与告警**：当实际内存使用接近物理内存时，自动调整超售比例

## 与Kubernetes内存管理的兼容性设计

### 核心设计原则：分层管理，互不干扰

**关键点：我们不修改 Kubernetes 原有的 cgroup 设置，而是在调度层面实现"逻辑超售"。**

### Kubernetes 原有内存管理机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Kubernetes 原有内存管理流程                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│   1. Pod 请求资源                                                        │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │   resources:                                                     │   │
│   │     requests:                                                    │   │
│   │       memory: "32Gi"     ← 调度依据                              │   │
│   │     limits:                                                      │   │
│   │       memory: "64Gi"     ← cgroup 硬限制                         │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                     │
│                                    ▼                                     │
│   2. Scheduler 调度决策                                                  │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │   节点可用内存: 128Gi                                            │   │
│   │   已分配 requests: 96Gi                                          │   │
│   │   剩余可调度: 32Gi                                               │   │
│   │   新 Pod requests: 32Gi  → ✓ 可以调度                            │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                     │
│                                    ▼                                     │
│   3. Kubelet 创建 cgroup                                                 │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │   /sys/fs/cgroup/kubepods/pod-xxx/                              │   │
│   │   └── memory.max = 64Gi (limits)                                │   │
│   │   └── memory.high = 60Gi                                        │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 我们的超售方案：修改调度器视角，而非cgroup

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Logical Memory 超售方案设计                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │                     核心思想                                     │   │
│   │                                                                  │   │
│   │   我们不修改 kubelet 设置的 cgroup，而是：                       │   │
│   │   1. 在 Scheduler 扩展中，使用"逻辑内存"替代"物理内存"作为       │   │
│   │      可调度资源的计算基础                                        │   │
│   │   2. 通过 Node 的 Extended Resources 或 Annotation 暴露         │   │
│   │      逻辑内存容量                                                │   │
│   │   3. cgroup 限制仍由 kubelet 按原有逻辑设置                      │   │
│   │                                                                  │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                                                          │

│   │   │   └── 这是真实的硬件资源                                    │    │

│   │   ├── K8S Allocatable Memory: 120Gi (预留8Gi给系统)            │    │
│   │   │   └── 这是 kubelet 报告给 API Server 的                     │    │
│   │   │                                                             │    │
│   │   └── Logical Memory: 200Gi (超售比例 1.67)   ← 我们的扩展      │    │
│   │       └── 这是我们通过 Extended Resource 暴露的                 │    │
│   │       └── 调度器使用这个值来判断是否可以调度                    │    │
│   │                                                                 │    │

│                                                                          │
```

### 具体实现方式对比

#### 方式一：Extended Resources（推荐）

```yaml
# Node 上报逻辑内存作为扩展资源
apiVersion: v1
kind: Node
metadata:
  name: worker-1
status:
  capacity:
    memory: 128Gi                          # 物理内存，K8S原有
    example.com/logical-memory: 200Gi      # 逻辑内存，我们的扩展
  allocatable:
    memory: 120Gi                          # 可分配物理内存
    example.com/logical-memory: 200Gi      # 可分配逻辑内存
```

```yaml
# Pod 使用逻辑内存资源
apiVersion: v1
kind: Pod
metadata:
  name: mysql-1
  annotations:
    logical-memory.k8s.io/enabled: "true"  # 标记为使用逻辑内存调度
spec:
  containers:
  - name: mysql
    resources:
      requests:
        memory: "32Gi"                      # K8S原生内存request
        example.com/logical-memory: "64Gi"  # 逻辑内存request（用于调度）
      limits:
        memory: "64Gi"                      # K8S原生内存limit（cgroup限制）
```

### 与K8S内存管理的完全隔离

| 层面 | K8S原生行为 | 我们的扩展 | 是否冲突 |
|------|-------------|-----------|---------|
| **调度** | 基于 requests 调度 | 提供 Extender，使用预测值调度 | ❌ 不冲突 |
| **cgroup limits** | kubelet 设置 memory.max | 完全不修改 | ❌ 不冲突 |
| **OOM Killer** | 基于 cgroup limits 触发 | 完全使用原有机制 | ❌ 不冲突 |
| **驱逐** | kubelet 基于 eviction threshold | 我们提前预警，但使用原有驱逐机制 | ❌ 不冲突 |
| **资源配额** | ResourceQuota 基于 requests/limits | 我们使用独立的 Extended Resource | ❌ 不冲突 |

## 深入理解：为什么逻辑内存不影响原生 MEM Request/Limit？

### 核心问题解答

**问题：K8S 的 MEM limits 是硬限制，逻辑内存方案怎么能不影响它？**

**答案：因为我们的方案工作在完全不同的层面，两者互不干扰。**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    K8S 内存管理的两个独立层面                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   层面 1: 调度层面 (Scheduler)                  层面 2: 运行时层面 (Kubelet)│
│   ───────────────────────────                   ─────────────────────────── │
│   • 决定 Pod 放到哪个节点                       • 实际运行容器              │
│   • 基于 requests 计算                          • 设置 cgroup 限制          │
│   • 发生在 Pod 创建时                           • 发生在容器整个生命周期    │
│   • 是"软"约束（只影响放置决策）                • 是"硬"约束（超限会被Kill）│
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                                                                      │   │
│   │   我们的逻辑内存方案只工作在【调度层面】                             │   │
│   │                                                                      │   │
│   │   • ✅ 修改: 调度器看到的"可用资源"                                 │   │
│   │   • ❌ 不修改: cgroup limits                                         │   │
│   │   • ❌ 不修改: kubelet 的内存管理                                    │   │
│   │   • ❌ 不修改: OOM Killer 行为                                       │   │
│   │                                                                      │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Request vs Limit 的本质区别

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Request 和 Limit 的作用域完全不同                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   resources:                                                                 │
│     requests:                                                                │
│       memory: "32Gi"     ← 调度保证：节点至少有 32Gi 空闲才能调度           │
│     limits:                                                                  │
│       memory: "64Gi"     ← 运行时硬限制：超过 64Gi 会被 OOM Kill            │
│                                                                              │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                                                                      │   │
│   │   Request 的生命周期:                                                │   │
│   │   ┌────────────────────────────────────────────────────────────┐    │   │
│   │   │                                                             │    │   │
│   │   │   Pod 创建  →  Scheduler 读取 requests  →  选择节点        │    │   │
│   │   │      │              │                        │              │    │   │
│   │   │      ▼              ▼                        ▼              │    │   │
│   │   │   requests      判断是否            调度完成后              │    │   │
│   │   │   只是一个      能放下              requests 不再          │    │   │
│   │   │   数字！        这个 Pod            起任何作用！            │    │   │
│   │   │                                                             │    │   │
│   │   └────────────────────────────────────────────────────────────┘    │   │
│   │                                                                      │   │
│   │   Limit 的生命周期:                                                  │   │
│   │   ┌────────────────────────────────────────────────────────────┐    │   │
│   │   │                                                             │    │   │
│   │   │   Pod 运行  →  Kubelet 设置 cgroup  →  内核强制执行         │    │   │
│   │   │      │              │                      │                │    │   │
│   │   │      ▼              ▼                      ▼                │    │   │
│   │   │   limits        memory.max =         进程超限              │    │   │
│   │   │   传给          64Gi                 触发 OOM Kill!        │    │   │
│   │   │   kubelet                                                   │    │   │
│   │   │                                                             │    │   │
│   │   └────────────────────────────────────────────────────────────┘    │   │
│   │                                                                      │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
│   关键理解:                                                                  │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                                                                      │   │
│   │   1. Request 只在调度时使用，调度后就"用完就扔"                     │   │
│   │   2. Limit 在整个 Pod 生命周期内持续生效                             │   │
│   │   3. 两者互不影响：Request 大不代表实际能用多少内存                  │   │
│   │   4. 即使 Request = 0，Limit 仍然会限制内存使用                      │   │
│   │                                                                      │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 为什么修改调度层不会影响运行时？

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    调度层与运行时层的完全解耦                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   原生 K8S 流程:                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                                                                      │   │
│   │   Scheduler                              Kubelet                     │   │
│   │   ─────────                              ───────                     │   │
│   │   读取 requests: 32Gi                    读取 limits: 64Gi          │   │
│   │        │                                       │                     │   │
│   │        ▼                                       ▼                     │   │
│   │   检查节点可用: 128Gi                    设置 cgroup:               │   │
│   │   已用: 96Gi                             memory.max = 64Gi          │   │
│   │   剩余: 32Gi ≥ 32Gi ✓                          │                    │   │
│   │        │                                       ▼                     │   │
│   │        ▼                                  容器运行时:                │   │
│   │   调度到 worker-1                         超过 64Gi → OOM Kill      │   │
│   │                                                                      │   │
│   │   两个组件完全独立工作！                                             │   │
│   │                                                                      │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
```

### 总结

| 问题 | 答案 |
|------|------|
| 逻辑内存会修改 cgroup 吗？ | **不会**，cgroup 由 kubelet 设置，我们不修改 |
| 逻辑内存会影响 OOM Kill 吗？ | **不会**，OOM Kill 基于 cgroup limits，不变 |
| 逻辑内存会让 Pod 用更多内存吗？ | **不会**，单 Pod 内存上限由 limits 决定 |
| 逻辑内存的作用是什么？ | 允许调度更多 Pod 到同一节点 |
| 如果预测失误会怎样？ | 触发原生的驱逐机制，和正常 K8S 一样 |

### 算法详细说明

#### 1. Holt-Winters 三次指数平滑

适用于具有**趋势**和**季节性**的时间序列：

```
Level:    L_t = α(Y_t / S_{t-s}) + (1-α)(L_{t-1} + T_{t-1})
Trend:    T_t = β(L_t - L_{t-1}) + (1-β)T_{t-1}
Season:   S_t = γ(Y_t / L_t) + (1-γ)S_{t-s}
Forecast: F_{t+h} = (L_t + h×T_t) × S_{t+h-s}

参数:
  α = 0.2~0.5  (数据平滑)
  β = 0.1~0.3  (趋势平滑)
  γ = 0.1~0.3  (季节性平滑)
  s = 24       (日周期)
```

#### 2. ARIMA (AutoRegressive Integrated Moving Average)

适用于**平稳**或**可差分平稳**的时间序列：

```
ARIMA(p, d, q) 模型:

  Y'_t = c + φ₁Y'_{t-1} + ... + φ_pY'_{t-p} + θ₁ε_{t-1} + ... + θ_qε_{t-q} + ε_t

其中:
  p = AR阶数 (自回归项数)
  d = 差分次数 (使序列平稳)
  q = MA阶数 (移动平均项数)
  Y' = 差分后的序列

自动参数选择 (Auto-ARIMA):
  使用 AIC/BIC 准则自动选择最优 (p, d, q)
  通常搜索范围: p ∈ [0,5], d ∈ [0,2], q ∈ [0,5]
```

#### 3. Prophet (Facebook 时序预测)

适用于具有**多重季节性**和**节假日效应**的时间序列：

```
y(t) = g(t) + s(t) + h(t) + ε_t

其中:
  g(t) = 趋势函数 (线性或logistic增长)
  s(t) = 季节性函数 (傅里叶级数)
  h(t) = 节假日效应 (可选)
  ε_t  = 误差项

优势:
  - 自动检测变化点
  - 处理缺失数据
  - 对异常值鲁棒
```

### 模型评估与选择

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        模型评估指标                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│   1. MAPE (Mean Absolute Percentage Error) - 主要指标                   │
│      ┌─────────────────────────────────────────────────────────────┐    │
│      │                    n                                         │    │
│      │  MAPE = (100/n) × Σ |actual_i - predicted_i| / actual_i     │    │
│      │                   i=1                                        │    │
│      │                                                              │    │
│      │  优秀: < 5%,  良好: 5-10%,  可接受: 10-15%,  需改进: > 15%   │    │
│      └─────────────────────────────────────────────────────────────┘    │
│                                                                          │
│   2. RMSE (Root Mean Square Error)                                      │
│      ┌─────────────────────────────────────────────────────────────┐    │
│      │            ┌─────────────────────────────────────┐          │    │
│      │  RMSE = √ │ (1/n) × Σ (actual_i - predicted_i)² │          │    │
│      │            └─────────────────────────────────────┘          │    │
│      │                                                              │    │
│      │  对大误差敏感，适合检测异常预测                               │    │
│      └─────────────────────────────────────────────────────────────┘    │
│                                                                          │
│   3. R² (决定系数)                                                      │
│      ┌─────────────────────────────────────────────────────────────┐    │
│      │                   Σ(actual - predicted)²                     │    │
│      │  R² = 1 - ─────────────────────────────                     │    │
│      │                   Σ(actual - mean)²                          │    │
│      │                                                              │    │
│      │  R² = 1: 完美拟合,  R² = 0: 等于平均值,  R² < 0: 差于平均    │    │
│      └─────────────────────────────────────────────────────────────┘    │
│                                                                          │
│   选择策略:                                                              │
│   ┌─────────────────────────────────────────────────────────────────┐   │
│   │  1. 默认使用 MAPE 最低的模型                                    │   │
│   │  2. 若 MAPE 接近 (差距<1%)，选择 RMSE 较低的                    │   │
│   │  3. 集成预测: 加权平均 top-3 模型                                │   │
│   │     weight_i = (1/MAPE_i) / Σ(1/MAPE_j)                         │   │
│   └─────────────────────────────────────────────────────────────────┘   │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

```
│                    Buffer Pool 变更处理策略                              │

│                                                                          │
│   核心思想: 使用 usage_ratio 而非绝对值进行预测                         │
│                                                                          │
│   场景: Buffer Pool 从 32GB 增加到 64GB                                 │

│   │   └── usage_ratio: 0.60                                         │   │
│   │                                                                  │   │
│   │   变更后 (预期):                                                 │   │
│   │   ├── Buffer Pool: 64GB                                         │   │
│   │   ├── 短期实际使用: ~19.2GB (不变)                               │   │
│   │   ├── 短期usage_ratio: 0.30 (下降!)                             │   │

│   │   3. 72小时后，逐步恢复正常预测                                  │   │
│   │                                                                  │   │
```

## 监控告警系统

### 告警级别与自动响应

| 级别 | 触发条件 | 自动动作 | 恢复条件 |
|------|---------|---------|---------|
| **INFO** | 使用率 > 60% | 记录日志 | 使用率 < 55% |
| **WARNING** | 使用率 > 75% | 逐步降低超售比例 | 使用率 < 70% |
| **CRITICAL** | 使用率 > 85% | 立即降至 1.0，限制调度 | 使用率 < 80% |
| **EMERGENCY** | 使用率 > 95% 或 OOM | 触发驱逐 | 使用率 < 85% |
